GOAL: today every agent daemon (agent/agensis-cli/src/agensis.mjs) only ever talks to the
hub server (server/index.cjs, Fastify + WS/realtime + Postgres). All messaging, job
dispatch, and status updates round-trip through the hub even when two agent daemons are
on the same LAN and could talk directly. We want:

1. DISCOVERY — a daemon can discover peer daemons on the same local network (same
   workspace, same LAN/mesh), not just agents the hub tells it about.
2. ADVERTISE-TO-HUB — a daemon advertises its direct-reachability (address/port/transport)
   and availability back to the hub using the SAME fire-and-forget pattern already
   established for agent_capabilities_sync / the heartbeat capability-drift-sync (see
   memory: heartbeat-capability-drift-sync, agent-state-files-feature; code:
   server/index.cjs capabilitiesDriftNudges, agent_connections.capabilities jsonb column).
   Do not invent a second sync mechanism — extend the existing one.
3. DIRECT CHANNEL — when two daemons are both reachable, job handoff / collaboration
   messages go directly daemon-to-daemon instead of hub-relayed, with a fallback to
   hub-relay when direct isn't reachable (NAT/different network/offline).
4. UI MUST NOT CHANGE SHAPE — the agents list keeps showing spoke agents nested under a
   hub agent (workspace_agents rows, existing agent-list hierarchy/UI in
   src/components — e.g. AgentsWindowContent.tsx). This is true regardless of whether a
   given message actually went direct or via hub relay: the hub is always informed and
   always the source of truth for "this agent exists and is part of this workspace,"
   direct connectivity is purely a data-path optimization underneath that.
