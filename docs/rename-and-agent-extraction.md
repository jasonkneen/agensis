# Rename `open-hatch → agensis` + extract open-source `agensis-agent`

> Status: planning. Executable checklist for the future migration. Nothing here
> has been done. Companion to `docs/architecture-agents-silos-farm.md`.

Two independent moves that can happen separately:

- **A. Rename** the closed repo `open-hatch → agensis` (metadata + docs only).
- **B. Extract** `agent/` into a NEW public repo `jasonkneen/agensis-agent`,
  and publish `@agensis/agensis-agent` from there instead of this monorepo.

Do A first (cheap, reversible), then B (git surgery). They are decoupled.

## A. Rename open-hatch → agensis

GitHub keeps redirects on rename, so this is low-risk, but pin these:

1. **GitHub**: Settings → rename repo to `agensis`. (Old URLs auto-redirect.)
2. **Local remote**: `git remote set-url origin https://github.com/jasonkneen/agensis.git`
3. **`AGENTS.md`** line ~167: `--repo jasonkneen/open-hatch` → `jasonkneen/agensis`
   (the GitHub-release install fallback command).
4. Grep for other literals: `grep -rn open-hatch . --exclude-dir=node_modules --exclude-dir=release`.
   Source hits are `AGENTS.md:167` only. (`package.json` name is already
   `agensis`; agent `repository.url` already says `agensis.git`.)
5. **Desktop auto-updater** (easy to miss): the built app's
   `release/**/Open Hatch.app/Contents/Resources/app-update.yml` has
   `repo: open-hatch` + `updaterCacheDirName: stursky-open-hatch-updater`. These
   files are regenerated by electron-builder, so fix the SOURCE — the
   electron-builder `publish` config (and the app/product name if you rebrand
   "Open Hatch" → "Agensis") — or shipped desktop apps check the wrong repo for
   updates after the rename. Find it: `grep -rn 'open-hatch\|Open Hatch' package.json electron-builder* build* 2>/dev/null`.
6. **CI**: `.github/workflows/publish-agent.yml` uses `${{ github.repository }}`
   implicitly via checkout — no hardcoded `open-hatch`, so nothing to change.
7. After rename, confirm `github.com/jasonkneen/agensis` resolves (200) and the
   agent `package.json` `repository.url` is no longer a 404.

> Note: the daemon `repository.url` ALREADY points at `agensis.git`. Until the
> rename lands, that link 404s. Renaming fixes it; no package edit needed.

## B. Extract `agent/` → public `jasonkneen/agensis-agent`

### Why it's safe

The web app never imports the daemon. Verified: the only `agensis-cli` /
`agensis-agent` references in `src/` and `server/` are **string tags**
(`source: 'agensis-cli'`, `runtime: 'agensis-cli'`), not code imports. The daemon
is a clean leaf. The one build coupling is the root `package.json` dev-dep
`"agensis-cli": "file:agent/agensis-cli"` (used only so the repo can lint/typecheck
the CLI source), which the extraction removes.

### Decision: keep history?

`git rev-list --count HEAD -- agent/` = **65 commits** touch `agent/`. Preserve
them with a subtree split rather than a bare copy.

### Steps

1. **Split with history** (from a clean clone of this repo):
   ```bash
   git subtree split --prefix=agent -b agent-split
   # → creates a branch whose root is the agent/ subtree, history intact
   ```
2. **Seed the new public repo**:
   ```bash
   gh repo create jasonkneen/agensis-agent --public
   git push git@github.com:jasonkneen/agensis-agent.git agent-split:main
   ```
3. **Restructure inside `agensis-agent`** so the two packages sit at the root
   (they are currently `agent/agensis-cli` + `agent/agensis-agent`). Choose ONE:
   - **Monorepo**: keep both as `packages/agensis-cli` + `packages/agensis-agent`
     with a root workspace. Preferred — the CLI *source* stays open too.
   - **Single package**: if the CLI and the published bundle collapse into one,
     flatten to root. More churn; only if you want to drop the src/bundle split.
4. **Fix the 6-site version contract references** so they resolve to the new
   layout (see `AGENTS.md` "Releasing the daemon"): both `package.json`s, both
   lockfile spots, `AGENSIS_CLI_VERSION`, `build.mjs` `SOURCE_VERSION`.
5. **Move the publish workflow**: `publish-agent.yml` moves INTO `agensis-agent`;
   the `agent-v*` tag trigger now lives there. Add `NPM_TOKEN` secret to the new
   repo (and fix the GitHub Actions billing that currently blocks CI publish).
6. **Cut the daemon out of this repo**:
   - `git rm -r agent/`
   - Remove root `package.json` dev-dep `"agensis-cli": "file:agent/agensis-cli"`
     and its two `package-lock.json` entries (root workspace ref + link node).
   - Remove the daemon sections from `AGENTS.md` (or replace with a pointer to
     the new repo).
   - Confirm `npm run typecheck && npm test && npm run build` still pass — they
     should, since nothing imports the daemon.
7. **Repoint docs**: the connect commands (`npm i -g @agensis/agensis-agent`)
   are unchanged for end users — the npm package name stays `@agensis/agensis-agent`.
   Only the *source home* moves.

### What must NOT change (or hosts break)

- The **npm package name** `@agensis/agensis-agent` — hosts do
  `npm i -g @agensis/agensis-agent@latest`. Keep the scope + name.
- The **connect protocol** (`agensis connect --url --token --workspace --agent`)
  and the WS auth frame — the agensis server speaks to whatever version is
  installed; keep the wire contract stable across the move.
- The **version stamping** (`build.mjs` asserts `SOURCE_VERSION` appears exactly
  once) — carry the whole 6-site contract into the new repo intact.

### Ordering with the Farm

The Farm CLI installs the daemon via `npm install -g agensis-cli` /
`@agensis/agensis-agent` (see `claude-farm/docs/distributed-silos.md`). As long
as the npm names hold, the Farm needs NO change when the source repo moves.
